# 云服务器

把 Google Cloud、AWS 与 Azure 机器当作普通的 OpsMaxx 服务器 —— 通过你已有的云厂商工具链访问，用的是你已有的登录态。

## 这是什么

一台藏在 IAP 之后的 GCE 实例、一台没有公网地址的 EC2 实例、一台只接受 Microsoft Entra ID 登录的 Azure VM：三台你既写不出地址、也不持有凭据的机器。云服务器让它们成为你连接列表里的一等条目。

OpsMaxx **不打包、不安装、也不重新实现** `gcloud`、`aws` 或 `az`，并且从不提议替你安装其中一个。它会找到你已经装好的那个，告诉你它找到的是哪个文件、是什么版本，然后使用它。你的云身份留在它该在的地方：如果你的组织使用 IAM、SSO、Entra ID、MFA 或条件访问，这些依然生效，因为 OpsMaxx 从没绕过它们。

> 云身份属于云厂商。OpsMaxx 只负责编排连接。

## 它编排连接，而不是包装命令

这是其余一切所依据的设计决定，值得说清楚，因为这个领域里很多工具做的是另一件事。

OpsMaxx 不是去跑 `gcloud compute ssh` 再把输出粘进终端。厂商 CLI 只被用于五件事 —— 探测、登录态、只读枚举、签发一份短期凭据、以及在没有地址时开一条隧道 —— 之后**由 OpsMaxx 自己去连**，用的是和其他所有服务器相同的 SSH 引擎。

```
添加服务器 → 选择云厂商
       │
       ├── 探测 CLI，确认你已登录
       ├── 枚举 projects / regions / instances
       ├── 签发一份短期凭据
       └── 若机器没有地址，开一条隧道
                │
                ▼
        一条普通的 SSH 连接
                │
   终端 · SFTP · 监控 · Docker · Kubernetes · 隧道 · 数据库
```

实际差别在于：云服务器不是「盒子里的一个终端」。因为拿到的是一条真正的 SSH 会话，**OpsMaxx 里其他一切都对它有作用**：文件浏览器、指标条、容器与 Kubernetes 视图、端口转发、经它打通的数据库，以及 MCP 工具。而如果只是包装厂商自己的 SSH 命令，你得到的就只有一个终端。

它还把一类风险**消除**掉，而不是去防御它。OpsMaxx 从不调用 OpenSSH，也从不透传 SSH 参数，因此不存在能被用来夹带本地命令的 `ProxyCommand` —— 那个本可承载它的字段根本不存在。

## 你需要什么

装好厂商 CLI 并已登录。别的什么都不需要，OpsMaxx 内部也不需要任何东西。

```bash
gcloud auth login          # Google Cloud
aws configure  /  aws sso login   # AWS
az login                   # Azure
```

连接编辑器会显示它找到了什么 —— 确切路径、版本，以及你当前以哪个账号登录 —— 出问题时也会说明缺的是其中哪一项。CLI 没装、会话未登录、会话已过期，是三个不同的问题、三种不同的解法，OpsMaxx 会指出你遇到的是哪一个，而不是报一句「连接失败」。

## 各厂商细节

### Google Cloud

选一个项目、一个区域（zone）和一台实例。**传输**默认是 *自动*：实例没有外部地址时经 IAP 开隧道，有地址时直连；两种都可以强制指定。

登录由 OS Login 签发。OpsMaxx 为这次连接生成一对密钥，把公钥以**五分钟 TTL** 发布出去，再由 IAM 决定你是否可以登录、以谁的身份登录。你的账号上不会留下任何长期注册的东西。

### AWS

选一个 profile、一个区域和一台实例，并给出要登录的 OS 用户（`ubuntu`、`ec2-user`）。**传输**设为 *自动* 时，在没有公网地址的情况下会使用 EC2 Instance Connect Endpoint。

EC2 Instance Connect 发布的密钥，实例只接受**六十秒**。这就是全部凭据：没有 `.pem` 需要分发、轮换或保管，崩溃遗留下来的一把密钥，在任何人能用它之前早已过期。

### Microsoft Azure

选一个订阅、一个资源组和一台 VM。认证方式是 **Microsoft Entra ID**，每次连接签发一张短期 SSH 证书。证书与其私钥放在一个临时目录里，连接结束即删除。

Azure 的另一条路 —— 用一个你已持有的密钥或密码的本地 VM 用户 —— 在这里被刻意排除。那不过是一台普通 SSH 服务器，而 **SSH** 连接类型已经能把它做好，背后还有保险库。

## 枚举

每一层都来自你自己的 CLI：先是项目 / profile / 订阅，再是区域 / resource group，最后是实例。已停止的机器会连状态一起列出，而不是被藏起来 —— 一台停掉的实例，很可能正是你想保存一个连接的。

每一层也都可以**手动输入**。枚举一个组织里的所有项目所需的授权，比访问其中一台实例更宽，因此枚举失败永远不会变成连接失败：列表会退回成一个文本框，并说明原因。

## 存了什么，没存什么

保存下来的云服务器只持有**标识符** —— 项目名与实例名、区域与实例 id、资源组与 VM。

从不保存：access token、refresh token、`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_SESSION_TOKEN`、Azure 令牌，以及任何密钥或证书。本来也没有什么可存 —— 凭据按连接签发，并会自行过期。明天再连时，用的是你厂商 CLI 那时的会话，而不是 OpsMaxx 今天抓下来的某一份。

加密备份里的云服务器只是几个字符串。它不携带任何能触达目标的途径，因为里面本来就没有可用于触达的东西。

## 看清它到底跑了什么

连接编辑器里有一处 **What OpsMaxx will run**（OpsMaxx 将运行什么；这一处目前仍显示英文），展示**真实的**命令 —— 由签发它们的同一份代码构建，因此预览不可能与实际行为发生偏离。它刻意**不**展示一句友好的 `gcloud compute ssh` 一行命令，因为 OpsMaxx 并不运行它，而把它打印出来，就等于在「你专门来查清真相的那个地方」给出一个看似可信的谎言。

开启调试日志时，用到了哪个二进制、是什么版本，会连同每条连接的生命周期一起记入调试日志。厂商输出在写入任何地方之前，都会经过与其他一切相同的脱敏层。

## AI 代理与云服务器

云服务器**完全可以被 AI 代理寻址**，和其他服务器一样，处在相同的访问组与审批提示之下。代理可以列出它们、连接、运行命令，并创建或修改云连接记录。

这是一次刻意的放宽，值得直说：触达一台云机器意味着在**你的**电脑上运行一个程序，因此代理可以让 `gcloud`、`aws` 或 `az` 启动起来。有两点约束着它，而且两点都是代码强制、而非约定：

- **代理只能选择标识符，永远不能选择命令。** 这条路径上没有任何地方接受命令字符串。每个参数都是一个参数数组的元素，由构建器组装，全程不涉及任何 shell。
- **每个标识符都做模式校验，且都不允许以 `-` 开头。** 看起来像选项的值会在任何进程启动之前被拒绝 —— 表单里查一次、代理写入时再查一次、从磁盘读回记录时再查一次、构建器里还要再查一次。

如果这个取舍不是你要的，可以拒绝 `manageServers` 能力，或把云服务器放进你的代理会话不覆盖的工作区。

## 明确的限制

- **不支持跳板机。** 云目标要么是一条本地隧道、要么是厂商解析出的地址，两者都无法由堡垒机承载。同时设置会被拒绝，而不是被忽略。
- **不支持 VPN 配置。** 理由同上；云目标本身就是传输通道。
- **仅 SSH。** 这条路径上没有远程桌面。
- **Azure 仅支持 Entra ID** —— 本地用户选项为何缺席，见上文。
- **崩溃可能留下仍在运行的隧道。** 正常退出 OpsMaxx 会随其所属连接一起拆除厂商隧道；被强杀则不会，一个残留的 `start-iap-tunnel` 或 `open-tunnel` 进程可能存活下来，可以从你的进程管理器里结束它。

## 证书

Azure 的 Entra ID 登录需要 OpenSSH 证书认证，而 OpsMaxx 使用的 SSH 库并未实现它。它由 `patches/` 中携带的一个补丁提供，安装时应用，并由一个对着真实 `sshd` 做认证的测试来兜底 —— 因为未打补丁的构建不会响亮地失败，而是失败成「Permission denied (publickey)」，看起来与 Azure 里的权限问题一模一样。
