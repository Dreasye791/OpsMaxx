# Internationalisation

OpsMaxx shipped English-only. This document describes the translation layer that
was added, how to extend it, and — importantly — what is still in English.

## 1. The one design decision everything else follows from

**The English string is the key.**

```ts
t('Settings')            // → 设置
t('{count} sessions', { count: 3 })   // → 3 个会话
```

Not `t('settings.title')`. Two reasons, both of which only matter once the
catalogue is thousands of entries deep:

1. **A miss has to degrade visibly and usefully.** With symbolic keys, a missing
   entry renders `settings.title` on a button — a screen that looks broken and
   says nothing. With the English source as the key, it renders `Settings`: the
   correct English, merely untranslated. Falling back to the source language is
   the only failure mode this layer is allowed to have, because it is the one a
   user can keep working through.

2. **Which makes partial coverage shippable.** A `t()` call can be added to a
   component before anybody has written its Chinese. The app is then partly
   Chinese rather than partly broken. That is what let the shell, Settings and
   the common surfaces be converted in one pass.

The cost, stated plainly: **rewording an English string orphans its
translation.** `npm run i18n:coverage` exists to report exactly that.

## 2. Layout

```
src/renderer/src/i18n/
  index.ts          the runtime: t, useT, setLanguagePreference, interpolation
  Trans.tsx         a sentence with markup inside it, kept as ONE key
  locales/zh-CN.ts  the catalogue, plus the glossary
  LocaleBridge.tsx  the single writer of the current language (renders nothing)
src/main/uiPrefs.ts the two things main owns: the menu labels and the --lang switch
scripts/i18n/
  coverage.mjs      coverage + orphan report (section 4)
  codemod.mjs       the one-pass wrapper (section 5)
  render-audit.mjs  what the running app actually shows (section 6)
tests/
  trans.test.tsx              the slot contract, asserted in English
  accessGroupSummary.test.ts  sentences composed at runtime, likewise
```

### Where the truth lives

The persisted choice is `settings.language` in the app store (`'system' | 'en' |
'zh-CN'`), because it is a user preference and belongs in the same file as the
theme. `i18n/index.ts` keeps a **mirror**, because `t` has to work outside React
— `store/toast.ts` builds messages and event handlers translate strings with no
component in sight.

`LocaleBridge` is the only writer of that mirror. It does three things on a
language change:

| what | why |
|---|---|
| `setLanguagePreference` | updates the runtime mirror |
| `document.documentElement.lang` | screen readers, CJK line-breaking, `:lang(zh)` CSS |
| `window.opsmaxx.i18n.set(locale, preference)` | main's menu labels, and the `--lang` switch remembered for next launch |

Both `locale` and `preference` cross that boundary. Sending only the resolved
locale would turn "follow the system" into a hard `'en'` the first time somebody
launched on an English machine.

### The shell

Chromium picks its `locales/*.pak` bundle from `--lang`, at startup, and never
looks again. `applyLanguageSwitch()` in `src/main/uiPrefs.ts` appends it before
`app.whenReady()`, reading a small file of main's own (`opsmaxx-ui-prefs.json`)
because the renderer's blob is not readable at that point.

That one switch buys more than the two labels in `menuLabel`. Every `role:` menu
item, the text-field context menu, the find bar and the spell-check panel all
come out of that bundle. Which is why `installMenu` names no label for undo,
copy or paste: writing one would **override** the translation with a hardcoded
English word.

`locales/zh-CN.pak` (571 KB) has been on disk the whole time. Nothing ever asked
for it because the switch was never appended.

### Typography

`global.css` has a `:lang(zh)` block covering four things a Chinese UI needs
that the Latin rules get wrong: a CJK-capable font stack (Geist ships no Han
glyphs, and the generic fallback is a serif on Windows), zeroed letter-spacing
(Han glyphs fill the em box, so Latin tracking pulls words apart), `line-break:
strict` (punctuation must not open a line), and `overflow-wrap: anywhere` on
prose surfaces only — not on `body`, because that would also allow a break
mid-path or mid-hostname.

## 3. Adding a string

```tsx
import { useT } from '../../i18n'

export function Thing(): React.JSX.Element {
  const t = useT()
  return <button title={t('Do the thing')}>Do the thing</button>
}
```

Then add the entry to `locales/zh-CN.ts` and run:

```
npm run i18n:coverage
```

Rules the catalogue itself documents:

- Keys must match the source **character for character**, including curly quotes
  (`“ ”`) and em dashes (`—`). A key that no longer matches orphans its
  translation silently — worse than never having written it, because the
  coverage report cannot see the difference.
- `{placeholders}` must be kept. Their position may move to suit Chinese word
  order.
- No separate plural entries. Chinese has no plural inflection, so
  `'{count} session'` and `'{count} sessions'` point at the same Chinese string.
  The ternary stays in the source because English needs it.
- A sentence with markup **inside** it is one key with named slots rather than
  several keys around the tags; adding it means `<Trans>`, not a fragment. See
  section 5.

### Translating at a leaf component

Three components translate their props rather than making ~90 call sites do it:
`EmptyState`, and both copies of `SettingSwitch`. This is safe and deliberate,
because the key is its own English text:

- a prop that is not in the catalogue comes back unchanged — which is what makes
  it harmless for the callers that pass something dynamic (a folder name, a
  server name);
- it is idempotent — `t` of an already-Chinese string finds no entry and returns
  it, so callers can be converted around it at any pace.

## 4. What `npm run i18n:coverage` does and does not see

It parses with the TypeScript compiler, not a regex, so it handles `t(` calls
that wrap across lines and does not mistake `t(` inside a comment for a call
site.

It reports both directions:

- **WIRED BUT UNTRANSLATED** — a `t('…')` with no catalogue entry. A worklist.
- **TRANSLATED BUT UNWIRED** — a catalogue entry nothing asks for. This is the
  defect the script exists for: nothing breaks and nothing warns when a label is
  reworded, but the translation silently goes dead.

**Its blind spot, stated plainly.** `t(it.label)` and `t(LABEL[a.kind])` are real
call sites whose string is only known at runtime. No static tool can check them.
The script counts them (currently 141) but cannot verify them, and it treats every
string literal in a file containing one as reachable so that registry-driven
names are not double-reported as both untranslated and orphaned. Files that hold
such a registry without calling `t` themselves are listed in `DYNAMIC_SOURCES`.

**A second blind spot, added with `<Trans>` (section 5).** The scanner looks for
`t('…')` calls, so a key that appears only as a JSX attribute —
`<Trans source="…" />` — is invisible to it: it can be neither reported as
untranslated nor reported as an orphan. Those keys escape the orphan report today
only by the reachability rule above, because every file that uses `<Trans>` also
contains a `t(expression)` call somewhere. That is a coincidence, not a check, so
a `<Trans>` key is currently verified by the render audit and by nothing else.
Reading the attribute is a small addition to the same AST walk.

**A third blind spot, which only the screen found.** The scanner looks for `t(`,
so copy that was **never wrapped at all** is not a gap to it — it is not counted,
it is not listed, and translating it would not move a single number. Six shapes of
it survived the codemod pass, and they are worth recognising individually because
each looks different at the call site:

- a literal inside a JSX expression — `{cfg.hasUrl ? 'A URL is saved…' : 'Stored
  with your other secrets…'}`, `{!cfg.hasUrl && ' Add a URL below to enable this.'}`;
- a multi-line JSX text block with inline markup in it — `… fixed at
  <strong>85%</strong>: a root filesystem past that alerts …`;
- a prop that is not one of the copy attributes — `message="No secret on this
  machine is readable without it. …"`; or an accessible name, as in
  `label="Check servers in the background"` on `Switch`, which does **not**
  translate its own label, unlike the `SettingSwitch` next to it, which does;
- a **runtime template string** — `` `Backup passphrase (min ${MIN_PASSPHRASE}
  characters)` `` — which no literal key can ever match, so an entry written
  against the rendered text is dead on arrival;
- copy **returned by a function** (`alertCoverageText()`, `alertCoverageLines()`)
  and rendered bare at the call site;
- copy that **is wrapped but has no entry**, because the string is assembled from
  parts (the `+`-built constants in `shared/`) or because one piece of a sentence
  never got a key. Invisible in the other direction: the call site exists, the
  entry does not, and no report says so.

Two tells. A few already had entries in the catalogue and were simply never
wired, which is why they also sat in the orphan list. And the `+`-built constants
can be checked mechanically: join the pieces the way the engine does, then look
for that exact text in the catalogue — which is the pass section 7 describes.

**The consequence to remember:** the headline percentage covers literal call
sites only. A registry string with no translation is *reachable*, therefore not
an orphan, therefore not reported — it will simply render English. Translating a
registry means reading it and doing it by hand.

## 5. Wrapping the copy: `npm run i18n:codemod`

`t()` cannot reach a string that is not inside it, and the app had ~2,000 such
strings across 160-odd components. `scripts/i18n/codemod.mjs` wraps them in one
pass — JSX text nodes, and the attributes that hold copy rather than
configuration (`title`, `placeholder`, `aria-label`, `label`, `desc`, …) — and
inserts `const t = useT()` into the component that owns each one, plus the
import.

It parses with the TypeScript compiler rather than with a regular expression,
because every rule it needs is one a regex gets wrong:

- **The hook has to land in the right function.** A regex cannot find the
  enclosing component, so it puts `useT()` at module scope (where it is not even
  legal, and where `t` would not be reactive) or in an inner arrow, where the
  component's own render never re-runs.
- **The key is the RENDERED string, not the source string.**
  `<div>\n  Hello\n  world\n</div>` renders `Hello world`; JSX collapses the
  newlines and trims each line. The catalogue is written against the rendered
  form, so the codemod reimplements Babel's own whitespace rules.
- **Edge whitespace is load-bearing.** `<b>bold</b> and text` renders as
  `boldand text` the moment the leading space is dropped. The codemod emits
  `{' '}` on whichever side the original had one, so the space is preserved
  outside the key.
- **Module-scope JSX is data.** `ACTIVITY_ITEMS` in ActivityBar and
  `SECTION_ICONS` in Settings are evaluated once at import, long before a
  language has been read back off disk. A `t()` there freezes the app in
  whatever it started as, and there is no function to hook. It is left alone.
- **`t` is a popular loop variable here** — `toasts.map((t) => …)`,
  `stores.map((t) => …)`. A `t('Copy')` inside such a callback resolves to the
  parameter, and the failure reads as `Type 'Toast' has no call signatures`
  rather than as a shadowed translator. The check is per node: 153 strings sit
  inside a scope that binds `t` and are left for a hand.

What it deliberately does **not** touch: string literals in `.ts` files and
string literals in `.tsx` outside JSX. A bare `'Saved'` in a store, a toast, a
title passed to `toast()`, or an error built by concatenation is a judgement
call each time — is it user-visible? is it already inside a component that will
translate it? `npm run i18n:coverage` lists what is left.

### Which function the hook goes into — and the black window it caused

The hook must land in a **component**, and the first version of this script
looked for the *outermost* enclosing function. That shipped, and the packaged app
opened on a black window.

Two files broke, both fatally, and neither is visible to `tsc` or to the
bundler:

| file | what the codemod did | what React did |
|---|---|---|
| `components/common/ErrorBoundary.tsx` | `const t = useT()` inside the class's `render()` | `Invalid hook call`. This is the ROOT error boundary — the one component with nothing above it to catch the throw — so nothing rendered at all. |
| `lib/deferredView.tsx` | `const t = useT()` inside the `deferredView` factory, which `App.tsx` calls **at module scope** | A hook during module evaluation, before React has a dispatcher. The bundle died before anything painted. |

The rule is now React's own naming convention: walk up from the JSX and take the
**nearest** function whose name starts with a capital letter, or `use` followed by
a capital (a custom hook). Anything else — a factory, a helper, an anonymous
callback, a class method — is not somewhere a hook may go, and is skipped and
counted rather than guessed at. Nested callbacks still work, because
`items.map(x => <li>…)` finds the component above it.

**The verification gap this exposed is the part worth keeping.** The chain used
for that change was `npm run typecheck` and `npm run build`, and *neither can see
a hook in the wrong place* — a hook in a class is a perfectly valid-looking
function call. What does see it is `react-hooks/rules-of-hooks`, which this repo
already runs:

```
node node_modules/eslint/bin/eslint.js src/renderer/src
```

That reports both failures by name (`cannot be called in a class component`,
`called in function "deferredView" that is neither a React function component nor
a custom hook`). Run it over the whole renderer, not a hand-picked list of
directories: the black window came from `components/common/`, which was outside
the scope of the lint run that was done before the codemod.

### The fragment problem, and `Trans`

JSX splits a sentence around inline emphasis, and each piece becomes its own
key:

```jsx
a machine that was <strong>stolen</strong> rather than retired
```

becomes three keys. English reads fine — each piece renders where it was. Chinese
does not: the pieces cannot be reordered, so "a machine that was **stolen**
rather than retired" cannot become 「一台**被盗**而非退役的机器」. Translating the
fragments produces word salad, and leaving them alone produces a Chinese
sentence with English holes in it.

`i18n/Trans.tsx` is the fix. The sentence stays ONE key and the markup becomes a
named slot:

```tsx
<Trans
  source="Access groups are for when the predefined profiles do not fit: an agent on the {b} profile does exactly what its group says, …"
  components={{ b: <b>{t('Custom')}</b> }}
/>
```

The translator puts `{b}` wherever their grammar wants it: the catalogue entry
reads 「…就该用访问组：处于{b}配置的代理会严格按自己的能力设置行事，…」 and the
slot lands between 处于 and 配置 with no space on either side. The fragment
version could not do that — the JSX around the element had to supply the spaces,
and they stayed in the Chinese (`处于 自定义 配置的代理`).

- `components` fills slots with nodes; `values` fills slots with text; a
  sentence needing both passes both. Often nothing is needed: a slot holding a
  count is a plain `t('… set each of the {n} individually', { n })`.
- A slot nobody filled keeps its `{name}` marker, the same choice `interpolate`
  makes for a missing var — a visible marker is a bug report, while dropping the
  slot deletes a word and says nothing.
- A missing entry renders the English source with its slots filled, so an
  untranslated screen degrades to English exactly as `t` does.
  `tests/trans.test.tsx` asserts that contract in English.

What a caller gives up: a slot is a node, so the slot's own text cannot be
reordered word by word by the translator. When the slot holds a translatable
phrase, the caller passes `t(…)` into it — which is why the example above has
`{t('Custom')}` inside `components`.

Fragments of one or two words still exist in a few places and are simply left
out of the catalogue; `Trans` is the way to bring each one in, not a reason to
wrap a word.

## 6. The render audit: `npm run i18n:render`

Wrapping and translating a call site and *seeing Chinese* are different facts,
and only the second one is the product. Three shapes render English while the
source looks wired, none of them visible to `coverage.mjs`:

1. **A data table in a `.ts` file whose values are rendered.**
   `components/onboarding/setupQuestions.ts` holds the persona names, the
   question text and every option label; `store/nav.ts` holds the AI and
   Settings page names. Nothing can be wrapped at the definition: a `t()` there
   runs at import, before `LocaleBridge` has read the store, so the string would
   be frozen in whatever language the module happened to load under. The fix is
   `t(row.label)` **where it renders** — safe because the key is the English
   source and `t` is idempotent.
2. **A module-scope table in a `.tsx` file**, same shape (`ACTIVITY_ITEMS`).
3. **A literal inside a JSX expression.** The codemod wraps JSX *text* and
   *attributes*; it does not touch `{busy ? 'Cancel' : 'Send'}`,
   `cancelLabel = 'Cancel'` in a destructuring default, or
   `` `More ${label} options` `` in a template literal.

So measure the finished thing:

```bash
npm run build && npm run i18n:render
```

It launches the built app under the screenshot demo profile, attaches over the
Chrome DevTools Protocol, dismisses onboarding, clicks every rail button **and
every section its second-level rail offers**, and reports per screen how much of
the visible text and of every `title` / `placeholder` / `aria-label` / `alt` is
Chinese — plus the exact list that is not, ranked by how many screens it appears
on. That ranking is the worklist; translating by string length, which is what
the first two passes did, optimises for the wrong thing.

Walking only the top level is the single most misleading thing this tool can do.
Both Settings (fifteen sections) and AI & MCP (seven) render their pages through
the same `.settings-nav` rail, so a top-level-only run reports the one section
that happens to be selected and says nothing about the other twenty-one — which
is how a 66% headline sat on top of a settings page that was mostly English.
The honest number at the time was 23%.

Three defects in the walk itself, each caught because a number looked wrong
rather than because anything failed:

- **A modal outlives the screen that opened it.** The bug-report button opens
  one; every later reading was the modal merged with the page behind it, which
  gave unrelated screens the same strings. Escape between screens.
- **A mounted-but-hidden panel still matches `.settings-nav .nav-item`.** A
  screen with no sub-navigation borrowed another panel's sections. Filter the
  items for visibility.
- **The first section must be clicked, not read.** It is not the selected one:
  the panel opens on whatever was last selected, so the reading labelled
  "General" was Appearance, and General was never opened at all. What gave it
  away was two sections reporting byte-identical numbers.

The number to watch is the Chinese share of **distinct strings**, not of call
sites: a screen is judged as a whole. 31% after the first wiring pass, 23% once
the second level was actually walked, 39% after the Settings and access-group
pass, and **87%** after the panels, the monitor tables, the onboarding flow and
the AI & MCP sections were done.

The audit has one structural limit worth knowing before reading a number off it:
it can only walk what the screenshot demo profile can reach, and that profile has
no servers, no cluster, no database, no VPN profile and no paired device. Screens
behind those — Kubernetes, Alerts, Access, Capacity, Addy, the VPN form — are
never opened, so work on them is invisible here in both directions: it cannot be
reported as a gap and it cannot be credited. Use section 4's source list for
those, and this audit for everything it can actually see.

Two environment notes, both of which cost a launch each to work out:
`ELECTRON_RUN_AS_NODE` must be removed from the environment or `electron.exe`
degrades to node and no window opens; and the sandbox here cannot start a GPU
process, so the audit passes `--no-sandbox --disable-gpu --in-process-gpu`.

## 7. Current state

Two tools, two numbers, measuring different things. Both are honest; read them
together before deciding what to do next.

**Source side** — `npm run i18n:coverage`, which reads every `t('…')` in the
tree:

- literal call sites (distinct strings): **2,761**, of which **1,347 (49%)** are
  translated;
- dynamic call sites `t(expression)`: **150**, not statically checkable;
- catalogue entries: **2,012**;
- wired but untranslated: **1,414**;
- translated but unwired (orphans): **442**.

**Screen side** — `npm run i18n:render`, which drives the built app and reads
what is on screen across every rail destination and every second-level section:

- **92% Chinese** of 784 distinct strings, across **41 screens**.

**Why 49% and 92% are both true.** The source list is every string in the app.
The audit sees only what the demo profile can reach, and that profile has no
servers, no cluster, no database, no VPN profile and no paired device. Whole
screens — Kubernetes, Alerts, Access, Capacity, Addy, the VPN form — are never
opened, so they sit inside that 1,414 and are *invisible to the audit in both
directions*: it can neither report them as a gap nor credit the work once done.
Read that as the shape of the remaining work rather than as comfort: the part of
it a screen can confirm is much smaller than the part it cannot.

Of the 1,414, 639 are under 20 characters, 450 are 20–60, 175 are 60–120, and 150
are longer than that — the last group being the prose. By file, the eleven largest
are `monitor/AlertsPanel` (56), `monitor/AccessPanel` (51),
`monitor/CapacityPanel` (44), `addy/AddyPanel` (43), `monitor/JobsPanel` (39),
`monitor/PosturePanel` (38), `ai/ApprovalDialog` (30), `vault/VaultView` (28),
`processes/ProcessesPanel` (23), `inspect/InspectView` (23) and
`http/collection/CollectionTab` (22). `kubernetes/KubernetesPanel` used to lead
that list at 67 and is now down to 8, which are API type names and `kubectl`
flags and stay English on purpose.

**What is still English on screen, and why.** 66 distinct strings, and every one
of them is on purpose. 64 are names: product words and key names (`Ops`, `Maxx`,
`Ctrl`, `Docker`, `HTTP`, `Kubernetes`), protocol and tool names (`SSH`, `SFTP`,
`VPN`), shell and colour-scheme names (`Git Bash`, `Solarized Dark`), and
commands and config snippets (`claude mcp add …`, `{"mcpServers": …}`,
`Authorization: Bearer <token>`). The last two are the timestamped diagnostic
block the bug-report screen renders, which changes on every run and is data
rather than copy.

**The class that used to be here is closed.** The 38 strings that read as copy
have been wired and translated: section 4's third blind spot lists the six shapes
they arrived in, and gap 2 records what closing it took. The tell they left
behind is worth knowing — two of them, `'Add a URL below to enable this.'` and
`'Check servers in the background'`, were *already translated* and simply never
connected, which is why they also sat in the orphan list.

One instrument detail worth knowing before counting that list: the audit reads
**DOM text nodes**, so a sentence with markup in it arrives in pieces —
`… Disk has its own, fixed at` is the first node of a paragraph in
`settings/Settings.tsx`, not a sentence of its own.

**One more way a live key looks dead.** Copy that reaches the screen through a
function — `alertCoverageText()` and `alertCoverageLines()` in
`settings/alertCoverage.ts` — is rendered as `t(expression)`, which no call-site
scanner can match. Those six entries appear in the orphan list although every one
of them is live on a screen, and the render audit is the only instrument that can
say so. The same holds for any key reached through a variable rather than a
literal.

**How to read the orphan list.** 439 sounds alarming; most of it is not a
defect.

- 406 are still literals in the tree, in files the scanner cannot follow:
  `lib/shortcuts.ts` (59), `components/onboarding/setupQuestions.ts` (51),
  `shared/mcp.ts` (42), `shared/modules.ts` (21), `components/addy/addyStatus.ts`
  (19), `http/sidebar/treeMenus.ts` (11), `main/index.ts` (10). They are
  translated at their render site through `t(expression)` — the blind spot
  section 4 describes.
- The remainder are either invisible because the source builds the key by `+`
  concatenation — `store/fleetStatus.ts` holds each sampler tooltip as a sentence
  plus a separate `'\n\nClick to unlock.'` tail while the catalogue holds the
  combination, so neither side is a literal the other can match — or genuinely
  dead after a rewording: `Go to Request Tab 1` … `8` (now built at runtime),
  `(Ctrl+E)`, `Last exported never.`

Translated so far: the application shell, the Settings navigation and all fifteen
of its sections, the whole onboarding flow, the AI & MCP panel — its navigation,
its capability table, its built-in access-group names, its prose and the card
summaries it composes at runtime — the Sync & devices panel, the monitor's
posture, inventory and capacity tables, the Kubernetes panel, the connection
editor, the VPN profile form, the update panel, the alert and backup settings,
every empty state reached from the rail, and the short strings across every
module: buttons, table headers, status names, field labels, tab names, shortcut
actions.

### Known gaps, in the order worth doing them

1. **The 1,414 literals `coverage.mjs` reports.** These are real `t('…')` call
   sites with no entry, so they are verified by re-running coverage — the count
   falls by exactly what you translate — rather than by looking at a screen.
   Largest first: `monitor/AlertsPanel` (56), `monitor/AccessPanel` (52),
   `monitor/CapacityPanel` (44), `addy/AddyPanel` (43), `monitor/JobsPanel` (39),
   `monitor/PosturePanel` (38), `ai/ApprovalDialog` (30), `vault/VaultView` (28),
   `processes/ProcessesPanel` (23), `inspect/InspectView` (23). Most of them live
   on screens that need a cluster, a database or a paired device, which is why the
   render audit can never confirm the work.
2. **The copy the codemod never wrapped — done.** This was the third blind spot,
   and closing it meant six shapes of work (section 4) across roughly sixty sites:
   ternary literals and bare text nodes throughout `settings/` (Webhook, SSH
   sessions, Settings, Backup, Machine grants, Backup destinations), two
   paragraphs plus a placeholder and two `title=` templates in `BackupPanel`, the
   no-entry fragments in `ai/AiPanel`, `ai/AiSecurity` and `BitwardenImport`
   (converted to `<Trans>`, because those sentences are split around `<code>`),
   the four `alertCoverage` sentences and their three render sites, the two
   `ProtocolLayout` shortcut pieces, and the six `+`-built constants in `shared/`
   — those needed entries only, because `SettingSwitch` and `NoteWhy` translate
   the props they are handed. Two of the strings were already translated and had
   simply never been wired.

   What the instrument that found them says now: **105 English strings on screen
   → 66**, and the remainder is names, commands, colour schemes and the two
   timestamped diagnostic blocks — nothing that reads as copy. Chinese went
   678 → 718, and each screen's share 87% → 92%.

   Three dead keys went with it: two carrying a hard-coded `min 12` that the
   template string could never match, and one that was a whole sentence the layout
   assembles from two pieces at runtime.
3. **Long descriptions in data tables — done, and worth recording how.** Checked
   by reading each file against the catalogue, because none of them contains a
   `t()` call to find: `shared/modules.ts` (39 values, including the module
   descriptions of 86–381 characters), `shared/mcp.ts` (44, the capability
   details) and `lib/shortcuts.ts` (50, plus 22 key names that are not copy).
   Nothing is missing. The same check is what any other registry needs, and
   section 4 explains why no tool will do it for you.
4. **`<Trans>` keys have no static check** (section 4). The render audit is the
   only thing that verifies them, and only on the screens it can open.
5. **Main process copy.** Roughly 60 user-visible strings, mostly error messages
   and MCP tool descriptions (`src/main/services/*`).
6. **Store copy.** `store/toast.ts`, `store/alerts.ts` and the approval
   announcement sentences in `store/approvalQueue.ts`.
7. **A second Chinese catalogue** for Traditional, if wanted. Nothing has to
   move: `CATALOGUES` takes another entry and `LANGUAGES` another option. All
   `zh-*` tags currently resolve to Simplified — and that is the moment to split
   the catalogue per locale and import it lazily (see Bundle cost).

### Bundle cost

The catalogue is a plain object inlined into the renderer bundle. It was 12 KB at
141 entries; it is now **1,959 entries, 209 KB of source across 2,658 lines**
before minification, and it lands in the main renderer chunk (`index-*.js`,
2.4 MB). The strings minify well, so the built share is smaller than the source
share — size is not the argument for splitting it, the doubling that a second
catalogue would bring is.

So the advice has flipped. Splitting per locale and importing lazily in
`setLanguagePreference` was premature at 12 KB; it is worth doing now, and the
natural moment is when a second catalogue lands (gap 7), because that is when the
object would otherwise double. It is not urgent on its own: the same object is
what makes a missing entry fall back to readable English, and no other part of
the design depends on it being one file.
